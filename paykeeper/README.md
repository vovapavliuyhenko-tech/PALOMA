# Оплата PayKeeper (Альфа-Банк) — Cloud Function

Сайт статический (GitHub Pages), поэтому логин/пароль от ЛК PayKeeper и
секретное слово хранить в нём нельзя. Они живут только здесь — в переменных
окружения функции в Яндекс Облаке.

```
checkout.html ──POST ?a=create──►  Cloud Function ──Basic auth──►  PayKeeper
      ▲                                                               │
      └────────────── редирект на ссылку оплаты ◄──────────────────────┘

PayKeeper ──POST ?a=webhook──► Cloud Function   (POST-оповещения в ЛК)
PayKeeper ──редирект─────────► thank-you.html?paid=1
```

Сервер PayKeeper: `https://paloma.server.paykeeper.ru`
ЛК: `https://paloma.server.paykeeper.ru/login` (логин `admin`)

## Что загружать в функцию

Перед каждой загрузкой выполнить в корне репозитория:

```bash
node paykeeper/sync.js
```

Он копирует сюда `paloma-products.js` и `coffee-menu-data.js` — по ним функция
пересчитывает цены. **После любого изменения цен на сайте — запустить снова и
перезалить функцию**, иначе сервер будет считать по старому прайсу.

В функцию загружаются: `index.js`, `package.json`, `paloma-products.js`,
`coffee-menu-data.js` (файл `test.js` на сервере не нужен).

## Настройки функции

**Таймаут — не меньше 30 секунд.** При 10 секундах функция успевала
отправить текст заказа, но не успевала догрузить фото букетов, и они
приходили через раз. Быстрые запросы от увеличения лимита не страдают.


| Параметр | Значение |
|---|---|
| Среда выполнения | `nodejs18` |
| Точка входа | `index.handler` |
| Таймаут | 30 секунд |
| Память | 128 МБ |
| Доступ | публичная функция |

Переменные окружения:

| Имя | Значение |
|---|---|
| `PK_USER` | логин ЛК PayKeeper (`admin`) |
| `PK_PASSWORD` | пароль ЛК PayKeeper (**секрет**) |
| `PK_SECRET` | секретное слово из ЛК → Настройки → POST-оповещения (**секрет**) |
| `PK_SERVER` | `https://paloma.server.paykeeper.ru` |
| `PK_SITE` | `https://paloma.website` |

## Настройки в ЛК PayKeeper

ЛК → **Настройки** → **Получение информации о платежах**:

- **Способ получения уведомления о платежах** → **POST-оповещения**
- **URL, на который будут отправляться POST-запросы:**
  ```
  https://functions.yandexcloud.net/<id-функции>?a=webhook
  ```
- **Секретное слово** — задать любое, и то же значение положить в `PK_SECRET`.
- **URL страницы, на которую клиент переходит при успешной оплате:**
  ```
  https://paloma.website/thank-you.html?paid=1
  ```
- **URL при неуспешной оплате:**
  ```
  https://paloma.website/checkout.html?payment=failed
  ```

## Подключение сайта

В `payment-config.js` в поле `PAYMENT_ENDPOINT` вписать адрес функции:

```js
PAYMENT_ENDPOINT: "https://functions.yandexcloud.net/<id-функции>",
```

Пока поле пустое — онлайн-оплата выключена, чекаут работает как раньше (заявка менеджеру).

## Защита цен

Сервер не верит ценам из браузера: они лежат в localStorage и их можно подменить.
`verifyCart()` сверяет каждую позицию с каталогом:

- букеты (`c1-…`) — от базовой цены до «база + максимальный размер + все допы»;
- кофе и десерты (`menu-…`) — по ценам из меню + максимум добавок;
- апселлы чекаута — точная цена;
- доставка — только 0 или 350 ₽;
- сертификаты/подписка/копилка — свободная сумма, но в границах 100…300 000 ₽.

POST-оповещение об оплате проверяется по подписи:
`key = md5(id + sum + clientid + orderid + секретное слово)`.
Ответ функции: `OK md5(id + секретное слово)`. Поддельные оповещения отбрасываются.

Проверить локально:

```bash
node paykeeper/test.js
```

## Тестовый → боевой режим

Кабинет пока в тестовом режиме. После успешной тестовой оплаты перевод в боевой
делает техподдержка PayKeeper (написать им, что тест прошёл).

## Касса (54-ФЗ)

Фискализация подключается на стороне Альфа/PayKeeper отдельно. Сайт уже передаёт
состав заказа (`service_name`) — этого достаточно для чека. Детали подключения

## CRM: заказы и заявки (crm.html)

Страница `paloma.website/crm.html` — рабочая панель: поиск, статусы,
заметки, выгрузка в Excel. Пароль — тот же `ADMIN_TOKEN`.

Данные лежат в таблице `crm_orders` (создаётся сама при первом заказе).
Это **не замена** `orders_log`: журнал остаётся страховкой «ничего не
потерялось», CRM — рабочий инструмент поверх тех же событий.

| Маршрут | Метод | Что делает |
|---|---|---|
| `?a=crm-list` | POST | список с фильтрами `q`, `status`, `kind`, `from`, `to`, `limit`, `offset` |
| `?a=crm-update` | POST | смена `status` и/или `note` по `orderId` |
| `?a=crm-import` | POST | разово перенести старые заказы из `orders_log` (идемпотентно) |

Пароль страница шлёт **в теле POST**, а не в адресной строке: query-строка
оседает в логах функции, тело — нет.

### После обновления функции — один раз

Открыть `crm.html`, войти и нажать «Обновить». Затем разово перенести
историю (в адресной строке браузера, подставив свой токен):

```
https://functions.yandexcloud.net/<id>?a=crm-import&token=<ADMIN_TOKEN>
```

Старые заказы приедут с номером, датой и текстом, но без полей клиента —
в журнале их просто не было. Новые заказы пойдут уже с полями.

## Каталог товаров (catalog-admin.html)

Страница `paloma.website/catalog-admin.html` — добавить товар, поменять цену
или фото, спрятать закончившееся, удалить проданное, переставить порядок.
Пароль — тот же `ADMIN_TOKEN`, шлётся в теле POST.

Товары лежат в таблице `products` (`id`, `slug`, `active`, `sort`,
`data JSONB`). В `data` — весь объект товара той же формы, что
`window.PALOMA_PRODUCTS` на сайте, поэтому фронту ничего перестраивать не
нужно. Фотографии — в таблице `product_images`, наружу отдаются ссылкой
`?a=img&id=…` (кэш браузера — год: под конкретным id файл не меняется,
новое фото получает новый id).

| Маршрут | Метод | Токен | Что делает |
|---|---|---|---|
| `?a=products` | GET/POST | нет | список активных товаров — его читает сайт |
| `?a=img&id=…` | GET | нет | отдать фотографию товара |
| `?a=products-migrate` | GET/POST | да | вернуть недостающие товары прайса (существующие не трогает) |
| `?a=products-all` | GET/POST | да | полный список для админки, вместе со скрытыми |
| `?a=product-save` | POST | да | создать или изменить товар (`product: {…}`) |
| `?a=product-delete` | POST | да | удалить насовсем (`id`) |
| `?a=product-active` | POST | да | показать/скрыть (`id`, `active`) |
| `?a=products-reorder` | POST | да | порядок вывода (`ids: [...]`) |
| `?a=product-image` | POST | да | принять фото (`dataUrl`), вернуть его id |

### Размеры букета

В `data.sizes` — массив `{ code, label, priceDelta }`. `code` уходит в id
строки корзины («m1-M») и в чек, поэтому чистится до латиницы и цифр;
`priceDelta` — доплата к базовой цене, отрицательной быть не может (иначе
поедет верхняя граница допустимой цены в `allowedRange`). `data.photoSize`
— код размера, который на фотографии: от него карточка каталога считает
показанную цену. У товара с единственным размером `photoSize` = null,
иначе у позиций с договорной ценой пропала бы приписка «от»
(`normalizeProduct` в `catalog-data.js` сбрасывает `priceFrom`, когда
`photoSize` совпал с размером).

### Как это связано с оплатой

Проверка цены на бэкенде обязана знать новые товары, иначе покупатель
увидит «Неизвестный товар». Поэтому перед разбором каждой корзины функция
подтягивает каталог из базы (`refreshCatalog`, кэш 60 секунд на тёплом
экземпляре). Если база недоступна — молча работаем по встроенному
`paloma-products.js`, старые товары продолжают продаваться.

Для проверки цены берутся и **скрытые** товары: скрытый букет мог остаться
у покупателя в корзине, с витрины он пропал, но оплатить его нужно дать.

### Первое открытие панели

Ничего нажимать не нужно: при первом заходе `products-all` сам переносит в
базу встроенный прайс (`autoSeed`). Повторно перенос не сработает — отметка
`catalog_seeded` лежит в таблице `app_settings`, поэтому удалённые вручную
товары не воскресают.

Перенос пишет **пачками по 50 строк**. Первая версия вставляла товары по
одному — 128 отдельных запросов в Neon не укладывались в таймаут функции,
она обрывалась на середине, и каталог оставался заполненным наполовину.

Если перенос всё же оборвался, лечится это из панели: `products-all` отдаёт
поле `builtIn` (сколько товаров в исходном прайсе), панель сравнивает его со
своим списком и предлагает «Вернуть недостающие» — маршрут
`?a=products-migrate` (`restoreMissing`). Он добавляет только отсутствующие
id, уже изменённые товары не трогает.

**Дальше источник правды — база, а не `paloma-products.js`.** Файл остаётся
запасным вариантом на случай, когда база недоступна; правки в нём на сайте
уже не появятся.
